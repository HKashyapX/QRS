# QRS v0.2.0 Dual-Lane Acquisition

## Purpose

v0.2.0 is the first physical spatial-multiplexing milestone. It replaces the single visible matrix
as the default with two independent 64×64 lanes while preserving one camera stream, one envelope
detection, and one file-recovery session.

This release is an experiment, not a throughput claim. It passes the milestone only if real-device
testing shows at least 1.6× the single-lane resolved goodput without worse completion reliability.

## Optical layout

The sender renders a connected portrait envelope:

- 3 black guard cells around the complete envelope;
- two vertically stacked 70×70 lane regions;
- each lane contains a 3-cell white quiet border and one 64×64 optical matrix; and
- no black gutter between lanes, so envelope detection sees one connected white component.

Lane 1 transmits A then B. Lane 2 transmits B then A. The opposite polarity keeps aggregate display
brightness steadier than two synchronized inversions, but every data cell still changes rapidly.
It therefore does not remove the photosensitivity risk or the need for a future non-flashing carrier.

## Shared receiver path

One camera callback performs these steps:

1. Draw the current camera image once.
2. Detect or reuse one outer-envelope quadrilateral.
3. Projectively divide the envelope into two lane quadrilaterals.
4. Sample and classify each lane into its own reusable buffer.
5. Pair A→B for lane 1 and B→A for lane 2.
6. Route both CRC-valid frames into one session and fountain decoder.

A classification or CRC failure in one lane is isolated. The other lane can still contribute during
the same camera frame.

## Acquisition refinements

- Preview processing increased from 640×640 to 720×720 to retain more of the camera's short-axis
  resolution.
- Tracker smoothing responds faster to handheld motion.
- Normal envelope detection refreshes every 133 ms instead of 200 ms.
- Two consecutive frames with no recognized lanes force immediate envelope reacquisition.
- The preview draws the shared envelope plus separate lane regions and recent lane-lock state.
- Diagnostics expose per-lane sampled, lock, failure, valid-pair, reject, routed-frame, and last-error
  values.

Dual lane halves the available display width per square if a portrait envelope must fit into the same
camera view. Keep `tracked camera pixels/cell` above 4 where possible. If it falls below that level,
move closer while preserving the complete black guard, or use single-lane compatibility mode.

## Controlled acceptance test

Use the same devices, file, distance, brightness, phase duration, and camera FPS for both runs:

1. Select **Single lane — compatibility** on sender and receiver.
2. Transfer a 10 KB binary at 50 ms/phase and 30 FPS. Save the full diagnostics.
3. Reset both pages and select **Dual lane — v0.2**.
4. Repeat without changing the physical setup. Save the full diagnostics.
5. Compare completion, resolved goodput, processing load, pixels/cell, pair acceptance, duplicate
   rate, and per-lane routed frames.
6. Repeat dual lane with the 60 FPS camera request only after the 30 FPS comparison.

The first field-test gate is:

- recovered bytes match the source;
- both lanes route valid frames;
- dual-lane resolved goodput is at least 1.6× the single-lane run;
- processing load remains below 900 ms/s; and
- neither lane remains below a 20% marker-lock rate for the complete run.

If dual mode misses the throughput gate, use the per-lane diagnostics to separate insufficient
pixels/cell from phase-order, tracking, and processing-load failures before changing the protocol.
