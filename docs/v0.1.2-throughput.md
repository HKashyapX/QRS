# QRS v0.1.2 Throughput Recovery

## Measured reason for this revision

The v0.1.1 physical test tracked 2,746 of 2,756 camera frames, proving that acquisition was no
longer the primary failure. It classified 1,701 observations but accepted only 38 of 246 attempted
phase pairs. Of the failed pairs, 203 reported insufficient cell contrast. Only 13 of 59 source
symbols resolved after 106 seconds.

Two implementation choices caused most of that loss:

1. The receiver consumed its A observation on the first recognizable B camera frame. A rolling-
   shutter or display-transition B therefore destroyed the pair before later clean B frames arrived.
2. Systematic source symbols were transmitted only once. A receiver that locked late had to depend
   entirely on the development LT repair distribution, which scales poorly for larger `K`.

## Changes

- Keep up to three quality-ranked A observations for the complete B window.
- Retry every later B observation until one A/B combination passes contrast, framing, and CRC.
- Ignore repeated B frames only after that logical frame has decoded successfully.
- Send four initial manifest frames and continue one manifest every 24 logical frames.
- Cycle two systematic source symbols for each fresh repair symbol indefinitely.
- Reduce cell sampling from nine points to a five-point quincunx.
- Run full frame detection every 200 ms and reuse the tracked homography between runs.
- Require six consecutive marker failures before forcing early reacquisition.
- Report pair observations, retries, retry recoveries, processing load, and estimated resolved
  bytes per second.

## Automated regression boundaries

- A deliberately mixed transition-B frame must fail without consuming the retained A window.
- A later clean B must recover the exact frame against that same A.
- A 59-symbol transfer that begins receiving after frame 120 and drops 70% of later data frames must
  still recover byte-for-byte from the continuing schedule.
- Rotation, reflection, fullscreen envelope, perspective acquisition, native C++, and browser-core
  tests remain required.

## Next physical test

Use exactly the same file and device placement as the v0.1.1 diagnostic run.

1. Confirm the sender reports the exact byte count and number of source symbols.
2. Start at 150 ms per phase and run for at least 90 seconds or until completion.
3. Copy receiver diagnostics.
4. Repeat at 220 ms only if transition, phase-pilot, or cell-contrast errors remain dominant.
5. Do not compare files by their filename description; compare exact sender bytes and source count.

The first success gate is not a theoretical maximum. On the same phone, v0.1.2 should materially
beat the v0.1.1 baseline of 0.36 valid frames/s, 15.4% pair survival, 34.1 ms average processing,
and 13/59 resolved symbols after 106 seconds. A useful target is at least 1 valid frame/s, at least
40% observed-pair survival, average processing below 30 ms, and continued systematic progress after
a deliberately late receiver start.
